# الجزء السابع: بنية الباك-إند والبنية السحابية

هالجزء بيحدد شو الخدمات، وكيف بتتواصل، وكيف بنضمن أمان وموثوقية وأداء بمستوى مؤسسي — بشكل يخلي كل مطوّر يعرف بالضبط وين يبني ميزة جديدة ووين حدود مسؤوليته.

## النمط المعماري: Modular Monolith يتطور لـ Services عند الحاجة

نبدأ بـ **modular monolith** — تطبيق واحد منشور، بس بحدود داخلية صارمة بين الموديولات (نفس حدود الجزء الثالث)، كل موديول بمجلده الخاص، بواجهة (interface) واضحة للتواصل مع باقي الموديولات، وممنوع الوصول المباشر لجداول موديول تاني إلا عبر تلك الواجهة.

**ليش مو microservices من اليوم الأول؟** لأن التعقيد التشغيلي لـ microservices (شبكة، تتبع موزّع، اتساق بيانات) غير مبرر قبل ما يكون في حاجة فعلية للتوسع المستقل. بس التصميم الداخلي (حدود الموديولات، الأحداث كوسيلة تواصل) مبني بشكل يخلي **فصل أي موديول لخدمة مستقلة لاحقاً عملية ميكانيكية، مو إعادة كتابة**.

**أول مرشح للفصل كخدمة مستقلة:** طبقة الـ AI Agents (الجزء الرابع) — لأنها الأكتر حساسية لموارد الحوسبة (compute-intensive) وبتحتاج تتوسع بشكل مختلف عن باقي النظام (queue-based, غير متزامنة بطبيعتها).

## الخدمات

| الخدمة | المسؤولية |
|---|---|
| **API Service** | الواجهة الرئيسية لكل طلبات الـ web/mobile clients. يحتوي كل الموديولات كـ modules داخلية. |
| **AI Worker Service** | تنفيذ مهام الـ AI Agents بشكل غير متزامن (async) — يستهلك من queue، ينفذ، وينشر النتيجة كحدث. |
| **Automation Engine Service** | يراقب الأحداث وينفذ الـ Workflows (موديول الأتمتة) — منفصل لأنه بيحتاج يشتغل باستمرار بالخلفية بغض النظر عن حركة المستخدمين. |
| **Notification Service** | يستهلك أحداث ويرسل إشعارات (داخل النظام، إيميل) — معزول لأنه high-throughput ومختلف تماماً بطبيعته عن باقي الخدمات. |
| **File/Asset Service** | بوابة موحدة للرفع والتنزيل من object storage، تشمل معالجة الصور/الفيديو (thumbnails, transcoding) قبل التخزين النهائي. |

## الـ APIs

- **API-First** (الجزء الثاني): كل قدرة بالنظام متاحة عبر API موثّق قبل ما يوجد أي واجهة مستخدم تستخدمها.
- **REST كنمط أساسي** للعمليات القياسية (CRUD على الكيانات)، مع **GraphQL layer اختياري** فوق نفس المنطق لحالات الاستعلامات المركبة (مثلاً: لوحة تحكم بتحتاج بيانات من 5 موديولات بطلب واحد).
- **Webhooks خارجية** لكل حدث مهم — تسمح لـ Integrations Hub (الجزء الثالث) وأي تكامل مستقبلي يشترك بأحداث النظام بدون polling.
- **إصدار API (Versioning)** صريح من اليوم الأول (`/v1/...`) — أي تغيير غير متوافق للخلف (breaking change) بياخد إصدار جديد، ما في تعديل صامت على عقد API قائم.

## المصادقة (Authentication)

- **جلسات مبنية على JWT قصيرة العمر + Refresh Token** للمستخدمين البشر (web/mobile).
- **SSO (SAML/OIDC)** كخيار للعملاء المؤسسيين (enterprise) — النظام مصمم من اليوم الأول يدعمه، مو يُضاف لاحقاً كـ patch.
- **API Keys** منفصلة تماماً عن جلسات المستخدم، لأي تكامل خارجي (Integrations Hub) أو استخدام برمجي مباشر.
- **AI Agents ما إلها "مستخدم" بشري** — كل Agent بيشتغل بـ service identity خاصة فيه، موثّقة بكل سجل نشاط (Event Log — الجزء الخامس)، هيك دايماً واضح "مين سوى شو": إنسان أو أي Agent بالاسم.

## نظام الصلاحيات (Authorization)

- **RBAC (Role-Based) كطبقة أولى** — أدوار معرّفة على مستوى المؤسسة (Admin, Account Manager, Creative, Finance...) — موديول Admin & Settings (الجزء الثالث) هو مصدر الحقيقة الوحيد لهاد.
- **صلاحيات على مستوى المورد (Resource-Level) كطبقة ثانية** — مثلاً مدير حساب معين يشوف بس عملاءه المخصصين له، مو كل عملاء الوكالة.
- **فرض مركزي (centralized enforcement)** — الصلاحيات ما بتتفحص بشكل متفرق بكل موديول لحاله، إنما عبر middleware/policy layer موحّد يمر منه كل طلب. هيك قاعدة "مين يقدر يشوف/يعدل شو" موجودة بمكان واحد قابل للتدقيق، متل مبدأ "مصدر واحد للحقيقة" (الجزء الثاني) بس مطبّق على الصلاحيات نفسها.
- **بوابات الموافقة (Approval Gates)** من الجزء الرابع مبنية فوق نفس نظام الصلاحيات — "مين يقدر يوافق على قرار AI حرج بهالنوع" هو صلاحية معرّفة بنفس المكان، مو منطق مبعثر بكل موديول.

## الكاشينغ (Caching)

- **طبقة Redis مشتركة** لثلاث أغراض منفصلة بوضوح: (1) كاش استعلامات قراءة متكررة (client profile, dashboard widgets)، (2) جلسات وrate limiting، (3) قوائم انتظار (queues) لمهام الـ AI Workers والـ Automation Engine.
- **إبطال كاش مبني على الأحداث (event-based invalidation)** — لما كيان يتعدل، بينشر حدث، والكاش المرتبط فيه بينمسح تلقائياً. ما في اعتماد على TTL فقط كحل وحيد، لتفادي عرض بيانات قديمة بلوحات التحكم.

## اللوجينغ والمراقبة (Logging & Observability)

- **Structured logging** (JSON) موحّد الشكل عبر كل الخدمات — كل سجل فيه `org_id`, `request_id`, `user_id` أو `agent_id` — قابل للربط والتتبع عبر الخدمات المختلفة لنفس الطلب (distributed tracing).
- **الـ Event Log نفسه (الجزء الخامس) هو جزء من طبقة المراقبة** — أي قرار AI أو تغيير حرج قابل للتتبع تاريخياً من قاعدة البيانات مباشرة، مو بس من ملفات لوج مؤقتة.
- **مراقبة أداء الذكاء الاصطناعي تحديداً** كفئة منفصلة: زمن استجابة كل Agent، معدل الاقتراحات اللي الإنسان بيرفضها (مؤشر جودة مباشر)، تكلفة الاستدعاءات (token usage) — لأن هاي المقاييس أساسية لصحة نظام AI-first، مو تفاصيل تشغيلية ثانوية.

## قابلية التوسع (Scalability)

- **معالجة غير متزامنة لكل ما هو ثقيل** — أي عملية AI، توليد ملف، أو تقرير كبير بتصير عبر queue (AI Worker Service / Automation Engine)، أبداً بشكل متزامن (synchronous) جوا طلب API عادي.
- **توسع أفقي (horizontal scaling)** لكل خدمة بشكل مستقل — الـ API Service وAI Worker Service بيتوسعوا بمعدلات مختلفة تماماً (استخدام AI بيتضاعف أسرع من حركة المستخدمين العادية عادةً)، فلازم يقدروا يتوسعوا بمعزل عن بعض من اليوم الأول.
- **تصميم Multi-Tenant من الأساس** (الجزء الخامس) — فلترة `org_id` مفروضة على مستوى طبقة الوصول للبيانات، مو ثقة بكل استعلام يتذكرها لحاله، وهاد أساسي للتوسع الآمن لمئات الوكالات بدون خطر تسرب بيانات.
- **Circuit breakers وrate limiting** على كل تكامل خارجي (Integrations Hub) — فشل أو بطء بخدمة خارجية (منصة إعلانية مثلاً) ما لازم يأثر على استقرار باقي النظام.

## الخلاصة لفريق التطوير

كل خدمة، كل API، وكل قرار بنية تحتية بهالجزء لازم يُقاس بنفس المعايير من الجزء الثاني: هل بيحافظ على مصدر واحد للحقيقة؟ هل الذكاء الاصطناعي طرف أساسي فيه مو إضافة لاحقة؟ هل جاهز لمقياس أكبر بعشر مرات من اليوم الأول؟ هل الأمان والصلاحيات جزء من التصميم مو طبقة تُلصق آخراً؟
